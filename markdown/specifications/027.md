---
title: "Spec 027 — macOS keybindings: Ctrl is not Cmd"
tags: [spec, keybindings, macos, platform]
status: done
---
From a friend testing a macOS build from source ([[Prompt25]]): "the keybindings are a mix of those intended for Linux and Windows — Ctrl+O acts like Cmd+O, Ctrl+N like Cmd+N. macOS users use Ctrl+N for Emacs-style cursor navigation."

**Cause.** `Keybinding::matches` took a single `ctrl_or_meta` flag and every caller passed `m.ctrl() || m.meta()`: one table for all platforms, at the price of *both* modifiers firing everywhere. On a Mac that makes Ctrl+O, Ctrl+N, Ctrl+S, Ctrl+P… application shortcuts, which on macOS they are not — Ctrl+letter belongs to the text system (Emacs keys in every text field) and Ctrl+click is the context menu.

**Done 2026-09-22.** `moonkale_ext_api::keys`: `is_mac()` (desktop: `cfg!(target_os = "macos")`; web: `navigator.platform`/`userAgent`), `primary(&Modifiers)` = Cmd on a Mac, Ctrl elsewhere — never both — and `primary_name()` so menus and the palette print `Cmd+O` on a Mac. Every site that said "Ctrl or Meta" now asks `keys::primary`: the frame's command dispatch, Ctrl+S in the CodeMirror, Rust and flow editors and the rich editor, Ctrl+click in the image viewer, both terminals (file links), git's Ctrl+Enter, and in the JavaScript bundles the wiki-link clicks (CodeMirror, Milkdown). The Rust terminal sends control bytes for **Ctrl** only, on every platform — Cmd+C on a Mac is copy, not `^C`. The keybinding text in Settings says so. Unit test on the rule; the keybinding-sensitive browser suites unchanged.

**Not verified on a Mac** — nobody in the project has one; the friend who reported it is the test. If Cmd+Q, Cmd+W or Cmd+, behave oddly in the webview, that is the next report. The CodeMirror and xterm bundles already used `Mod-` keymaps (Cmd on a Mac) and are untouched.

**macOS in Docker?** It exists (`docker-osx`: macOS in QEMU/KVM inside a container; needs KVM, tens of GB, slow), but Apple's licence allows macOS virtual machines on Apple hardware only, so it is not a route this project uses. The legitimate way is the GitHub macOS runner the release workflow already uses for `.dmg` builds — which builds but cannot click. Testing stays with people who own a Mac.
