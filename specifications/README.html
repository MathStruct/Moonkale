Planned — not yet numbered

Requests that are agreed but have no spec number yet. Daniel numbers them when he writes the spec; until then they live here.

  • Components on the canvas (2026-10-14). Small Dioxus components drawn over the graph and flow renderer, for example a table node in a schema editor (Supabase-like), a node’s settings edited in place, or an Obsidian-like canvas of documents. They show only when zoomed in far enough, and only a few at a time. The shape:

    • a DOM layer above the GPU canvas and the label overlay, moved by one CSS transform per camera change, with components placed in canvas coordinates;
    • a node marked as embedded keeps its rectangle in the engine (wires, ports, drag, layout); only its label and symbol give way to the component;
    • below a screen size or off-screen, the component unmounts and the plain rectangle remains;
    • clicks pass through the layer except on components, and a card’s header drags its node;
    • 2D only.

    Items 1–3 implemented in WP-04/05 (2026-10-23): the engine reports a frame-coalesced CSS-pixel camera mapping, and InNode.embed reserves a plain rectangle without label, caption, icon or schematic ink. The new shared packages/canvas-layer crate provides CanvasLayer, CanvasItem and CanvasHeader: one camera transform, world-space placement, size/viewport unmounting, component-only pointer handling and header drag callbacks. It rejects 3D views. Graph and future canvas editors can use it without depending on the flow extension.

    Flow is the first user: its selected block’s parameter card follows pan, zoom, fit and resize, and its header moves the document’s block with one undo step. Undo/redo retain selections that still exist in the restored scope. Flow limits automatic fit magnification so a single block leaves room for the card; explicit zoom remains free. The card remains beside its schematic; hosts replacing node content can use embed:true instead.

    Acceptance is covered by native camera/embed/visibility tests, graph-camera.mjs and the production-panel canvas-layer.mjs, alongside graph/flow/subflow suites. The layer unmounts below 100 × 32 projected CSS pixels or outside the viewport, leaving the engine node in place.

    Item 4 remains open: an extension node-kind contribution would resolve a host-side view factory returning a Dioxus Element plus world bounds and LOD limits. The host wraps it in CanvasItem, supplies its camera and node-drag callback, and marks the corresponding engine node embedded. The shared layer does not depend on a registry or extension API; the contribution contract and permissions can be added later without changing camera/placement plumbing.

  • Code editor at 60 FPS (2026-10-14): requirement CED-R22 in Code Editor Requirements, the gate in Rust Code Editor Roadmap. p95 frame interval ≤ 16.7 ms while typing, scrolling and selecting, in an ordinary file and the 3 MB one, web and desktop. The current Rust editor does not meet it yet.

  • A stripped-down static reader (2026-10-14, way later): a repository or a knowledge graph published as wiki-like pages, Quartz-like but with code navigation, Moonkale’s graph and in-browser SQL. It sits beside the full web version, not in place of it. Quartz stays for the vault until then. Notes in Publishing Sources (“Revisited 2026-10-14”).

  • Math in any delimiter, LaTeX or Typst (2026-10-14): $, $$, \(, \[ and their doubled-backslash forms all work. Each formula renders as LaTeX (KaTeX) or Typst math, whichever it is, and errors only when both fail. A command normalises a file or folder to one convention. Spec in Math Delimiters and Renderers, WP-36.

  • Shared work in a session (2026-10-14): several people and agents in one session (roles, agents with a sponsor, tasks, an approval inbox, attribution); concurrent edits on one graph, where the database guarantees each write and Moonkale adds awareness, conflicts, proposals and per-actor undo; comments on anything, with @agent mentions. In Shared Work, WP-48 to WP-50. Conversations already render Markdown.

  • Linked panels (2026-10-14): a node’s content and its context (the local graph, backlinks, rows, plots) form a link group that follows one subject. Each group has a tab colour plus a marker (never colour alone), and several groups can exist side by side, each with its own local graph. Plan in Linked Panels, WP-59.

  • Overview (2026-10-14): like GNOME’s Activities, Ctrl+Alt+Space (the Windows key isn’t available) shows every open tab across tiles and windows as a card with a schematic preview of its content, grouped by link group, with type-to-search that also reaches quick open. Plan in Overview, WP-60.

  • Monochrome mode (2026-10-29, way later, low priority). Daniel’s idea: a mode without colour, to make the screen less attention-grabbing. Some people report that it helps them concentrate.

    • Evidence:

      • studies of grayscale phones (for example Holte & Ferraro, 2020) found less screen time, with little or no effect on well-being;
      • nothing measured dopamine;
      • nothing studied work tools such as an editor.

      So it is a preference, not a proven aid.

    • Feasible because colour is never the only signal: link groups have numbered markers, and diffs, conflicts and diagnostics have symbols. The mode loses no information and doubles as a check of that rule.

    • Shape:

      1. a monochrome theme (grey --mk-* tokens), with content such as images, graphs and plots keeping its colour;
      2. optionally a “grayscale everything” switch, a whole-window filter like a phone’s, which also greys graph colours that carry meaning.

      Both live under Settings → Appearance, with a palette command to toggle them.
